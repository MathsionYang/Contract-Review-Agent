# 合同审查知识底座 · 索引与引用规范

本文件是知识底座的入口，定义**三库结构、ID 体系、引用语法、版本时点规则与冲突消解顺序**。
所有审查意见、审批记录、规则引擎输出中出现的引用，必须能在本底座中解析到唯一目标。

---

## 一、三库结构

底座由三类互相引用的知识资产构成，分别回答三个不同的问题：

| 库 | 代号 | 回答的问题 | 性质 | 可变性 |
| --- | --- | --- | --- | --- |
| 法律快照 | `LAW` | 法律怎么规定？ | 外部强制规范 | 随立法/修法变动，**企业无权修改** |
| 确定性规则 | `RULE` | 什么情况必须报警？怎么判定？ | 企业内部的机器可执行判断逻辑 | 可调阈值，须走变更审批 |
| 企业制度 | `POL` | 我们公司自己的红线在哪？ | 内部管理规范 | 企业自主制定，须履行民主/公示程序 |

三者的关系是：**`POL` 不能突破 `LAW`，`RULE` 是 `POL` 与 `LAW` 的可执行化表达。**

例如：

```
LAW-CIVIL-585（违约金可请求调整，超过损失 30% 一般认定过分高于）
        ↓ 落地为
POL-CON-6.4（违约金原则上按日 0.03%–0.05% 约定，双向对称）
        ↓ 可执行化为
RULE-BIZ-004（逾期付款违约金日费率 > 0.05% → 命中 P0）
RULE-BIZ-006（双向违约金倍差 > 5 倍 → 命中 P1）
```

## 三、ID 命名规则

### 3.1 法律条文

格式：`LAW-<法简称>-<条号>`

| 法简称 | 对应法律 | 示例 |
| --- | --- | --- |
| `CIVIL` | 中华人民共和国民法典 | `LAW-CIVIL-585` |
| `ARB` | 中华人民共和国仲裁法 | `LAW-ARB-18` |
| `CIVPRO` | 中华人民共和国民事诉讼法 | `LAW-CIVPRO-35` |
| `ESIGN` | 中华人民共和国电子签名法 | `LAW-ESIGN-13` |
| `DSL` | 中华人民共和国数据安全法 | `LAW-DSL-27` |
| `PIPL` | 中华人民共和国个人信息保护法 | `LAW-PIPL-13` |

带款次的引用写作 `LAW-CIVIL-585.2`（第 585 条第 2 款）。

### 3.2 规则

格式：`RULE-<域>-<三位序号>`

| 域 | 含义 | 判定特征 |
| --- | --- | --- |
| `FMT` | 形式与要素（form） | 纯确定性，不依赖业务知识 |
| `PRC` | 流程与文本完整性（process） | 要素完备性，**需要标的物属性作为上下文参数** |
| `BIZ` | 商务与法务（business） | 阈值判定 + 少量范围判断 |

序号在三个域内各自独立、不复用。规则作废时保留编号并标记 `废弃`，不得将编号分配给新规则。

**调用顺序**：`FMT → PRC → BIZ`，顺序不可颠倒（理由见 `RULE-PRC` 第三节）。

### 3.3 企业制度条款

格式：`POL-<制度简称>-<条号>`

| 制度简称 | 对应制度 | 示例 |
| --- | --- | --- |
| `PUR` | 采购管理制度 | `POL-PUR-7.3` |
| `CON` | 合同管理办法 | `POL-CON-6.4` |
| `AUTH` | 合同审批权限表 | `POL-AUTH-3.1` |

> **编号体系说明**：`POL-PUR`、`POL-CON` 采用"第 N.x 条"单一层级编号；`POL-AUTH` 采用"第 N 条 + N.x 款"两级结构，引用时统一写作 `POL-AUTH-N.x`。

## 四、引用语法

审查意见中引用知识底座，统一使用以下形式：

```
【风险】预付款比例为合同总价 100%，未与交付、验收挂钩
【等级】P0
【依据】RULE-BIZ-001、POL-PUR-9.2、LAW-CIVIL-626
【建议】调整为预付 30% / 到货验收 60% / 质保期满 10%
【参考话术】POL-CON-6.4
```

四条硬要求：

1. **每条风险至少一处 `RULE` 或 `POL` 依据**，涉及法律强制性规定的，并列 `LAW` 依据。
2. **不得引用底座中不存在或已废止的 ID**。引用前须能解析。
3. **等级由 `RULE` 的命中动作决定**，不由审查人的主观判断决定；确需突破时，须在意见中写明理由。
4. **引用 `LAW` 时须注明版本**（见第五节），不同版本条号可能不同。

## 五、版本与时点规则

### 5.1 版本声明

每份 `LAW` 快照头部必须声明：

- 法律名称与发布/修正信息
- **施行日期**
- 快照生成日期与核对方式
- 已知的条号变动情况

### 5.2 适用时点

判断某份合同适用哪一版规范，**以合同签署日（非审查日）为准**：

| 情形 | 适用版本 |
| --- | --- |
| 签署日在版本生效日之后 | 适用该版本 |
| 签署日在版本生效日之前 | 适用上一版本，并在意见中提示"签署时适用旧版" |
| 跨版本履行的长期合同 | 以签署日版本为准判断效力性问题；履行行为适用行为发生时版本 |

### 5.3 时效性检查

底座中每份 `LAW` 快照标注 `下次复核日期`。法务部应至少每 12 个月复核一次，并在下列事件发生后 30 日内完成专项复核：

- 法律修正、新司法解释出台
- 最高人民法院发布相关指导性案例或会议纪要
- 公司发生因该规范引发的争议案件

## 六、冲突消解顺序

当同一事项在不同来源给出不同结论时，按以下顺序适用（前者优先）：

| 顺序 | 来源 | 说明 |
| --- | --- | --- |
| 1 | 法律、行政法规的**强制性规定** | 违反则条款无效，无例外 |
| 2 | 《民法典》等法律的**任意性规定** | 合同约定优先，无约定时补充适用 |
| 3 | 企业制度（`POL`） | 内部红线，对外不产生效力，但构成审批依据 |
| 4 | 集团/上级单位规范性文件 | 适用于本文件未覆盖事项 |
| 5 | 行业惯例与交易习惯 | 仅在无前述依据且不违反公平原则时适用 |

**特别注意**：`POL` 的要求严于 `LAW` 时，`POL` 在内部审批中具有约束力（例如法律未禁止 100% 预付，但 `POL` 禁止）；`POL` 的要求宽于 `LAW` 的部分**一律无效**，以 `LAW` 为准。

## 七、维护流程

| 环节 | 责任方 | 产出 |
| --- | --- | --- |
| 触发（立法变动、制度修订、纠纷复盘） | 法务部 | 变更需求单 |
| 起草 | 法务部 | 修订稿 |
| 复核 | 财务部（涉钱条款）、内审部（涉流程条款） | 复核意见 |
| 审批 | 法务分管副总；`RULE` 阈值调整须经总经理 | 批件 |
| 发布 | 法务部 | 新版本文件 + 变更说明 |
| 归档 | 行政部 | 版本台账（保留全部历史版本） |

历史版本一律保留，不得覆盖，以便追溯某一时点审查所依据的规范。

## 八、核验声明

本底座中的法律条文为**审查参考摘编**，条文要点已对照全国人民代表大会、最高人民法院及国务院部门官方公布文本核对。但：

- 条号与表述**以官方公布文本为准**，重大引用前应再次核验；
- 摘编的目的是支撑合同审查判定，不构成法律意见；
- 涉及重大权益的合同，应取得执业律师的专项意见。

## 九、完整性校验（附录）

知识底座每次修订后应执行引用完整性校验，确保**所有被引用的 ID 均可在底座内解析**。校验脚本 `_verify.py` 保留在底座目录中，可直接重跑。

**本次校验结果（2026-09-17）**

| 校验项 | 结果 |
| --- | --- |
| 法律条文定义数 | **81 条**（覆盖民法典合同通则、买卖合同章、仲裁法、民诉法、电子签名法、数据安全法、个人信息保护法） |
| 确定性规则定义数 | **44 条**（`RULE-FMT` 16 条 + `RULE-BIZ` 22 条 + `RULE-PRC` 6 条，无缺号） |
| 制度条款定义数 | **118 条**（`POL-PUR` 47 条 + `POL-CON` 57 条 + `POL-AUTH` 14 条） |
| 悬空引用 | **0 处** ✔ |

校验方式：扫描全部文档中形如 `LAW-XXX-nnn`、`RULE-XXX-nnn`、`POL-XXX-n.x` 的引用，与各文件中的定义集合求差。**任何非零结果都视为阻断性缺陷**，须修复后才能发布新版本。

> **为什么要做这一步**：知识底座的价值完全建立在"引用能落地"上。一处悬空引用意味着审查意见指向了一个不存在的依据——这比没有依据更糟，因为它会让审批人误以为已经核实过。

**变更管理要求**：新增或修改 `RULE` 时，必须同步更新本文件第二节的文件清单与本节的数量数据；作废的规则编号**保留不得复用**，以防历史审查记录中的引用失去指向。
