# 合同上传后风险项生成与界面展示链路分析

> 文档类型：项目实战 / 功能链路分析
>
> 对应阶段：P0-P2 已实现能力，M3 可验收化前置分析
>
> 对应代码：`electron/main.cjs`、`electron/review-runner.cjs`、`electron/review-engine.cjs`、`electron/model-gateway.cjs`、`src/stores/review.js`、`src/App.vue`、`src/components/ReviewWorkspace.vue`、`src/components/DashboardView.vue`
>
> 当前状态：后端风险生成和审查工作区展示已实现；上传过程中的可见性、结果解释和异常引导仍不完整
>
> 编写日期：2026-09-15

## 1. 结论摘要

当前系统在模型配置完成后，上传合同并不会在 `contract:import` 阶段直接产生风险项。真实链路是：

```text
模型配置 / 规则与知识配置
  -> contract:import：解析合同、创建项目和审查任务、初始化 risks=[]
  -> 前端 importContract：保存状态并自动调用 runReview()
  -> review:run：执行规则、知识依据检索、analysis 模型调用和结果归一化
  -> 合并为 review.risks
  -> Electron 保存 state.reviews[projectId]
  -> Pinia store.risks 响应式更新
  -> Dashboard 统计 + ReviewWorkspace 风险清单与详情
```

因此，风险项的真实来源是审查任务的结果，而不是合同文件对象或模型配置列表。风险项最终落在：

```text
state.reviews[当前项目 project_id].risks
  -> store.review
  -> store.risks
  -> ReviewWorkspace.filteredRisks
```

当前“界面没有体现”的感受有两种可能，必须区分：

1. **执行期间不可见**：上传弹窗会等待导入后的整次 `runReview()` 完成，随后才关闭并切换到“审查工作区”。用户在模型请求、知识检索或规则执行期间看不到任务步骤和风险增量。
2. **执行完成后仍为空**：这通常不是展示组件不存在，而是没有满足模型、规则、知识、解析或返回格式条件，导致只保留规则结果、结果为空，或任务进入 `partial` / `failed`。

代码中已经存在“本次审查执行配置”“审查任务进度”“风险清单”“风险详情”和 Dashboard 风险统计，但它们没有在上传过程中组成一个连续、可解释的反馈闭环。

## 2. 真实功能链路

### 2.1 模型配置只提供执行能力

能力配置页面保存的是模型执行配置，不是风险结果。配置主要包含：

- 配置名称、模型标识和服务商；
- API 地址、凭据引用；
- 模型角色，例如 `analysis`、`extraction`、`embedding`、`rerank`；
- 上下文长度、最大输出 Token、超时和重试次数；
- 状态、配置版本、数据策略和测试状态。

审查编排通过 `executionModel(state, review, "analysis")` 选择语义分析模型。应至少确认以下条件：

| 条件 | 作用 | 未满足时的影响 |
|---|---|---|
| `role=analysis` | 表明模型可用于风险分析 | 不会被完整审查的分析步骤选中 |
| `status=active` | 表明模型已启用 | 只能显示配置，不能作为执行模型 |
| `modelId` 非空 | 用于请求体的 `model` | 网关返回 `MODEL_CONFIG_INVALID` |
| `endpoint` 非空 | 用于构造 `/chat/completions` 地址 | 网关返回 `MODEL_CONFIG_INVALID` |
| `testStatus=passed` | 前端聊天模型列表的严格准入条件 | 对话审核不可用；执行快照也可能不采用模型 |
| 凭据引用可解析 | 主进程可获得 API Key | 返回“模型凭据引用不可用” |

当前实现有一个需要在验收时注意的细节：`src/stores/review.js` 中 `activeAnalysisModels` 对聊天模型要求 `testStatus === "passed"`；`electron/review-runner.cjs` 的执行选择对未定义的 `testStatus` 兼容放行，但仍要求模型处于启用状态并有完整地址和标识。实际操作应采用更严格的做法：保存配置、校验通过、启用模型，再上传合同。

模型配置成功本身不会生成风险。它只是让后续 `review:run` 能够向模型发送合同文本和已检索依据，并尝试取得结构化风险结果。

### 2.2 `contract:import` 阶段只创建审查任务

Electron 主进程的 `contract:import` 处理器执行以下工作：

1. 校验并解析 DOCX 或 PDF；
2. 复制原始文件到项目存储目录，生成文件版本和哈希；
3. 创建 `project`；
4. 创建 `review`；
5. 绑定当前已选的法律快照、规则和企业制度；
6. 创建一个状态为 `queued` 的审查任务；
7. 将初始审查状态保存到本地。

初始审查对象明确包含：

```js
{
  risks: [],
  config: {
    snapshot: { id: "", status: "draft" },
    rules: [],
    policies: []
  },
  task: {
    status: "queued",
    current_step: "parse",
    progress: 0,
    checkpoint_id: "...",
    idempotency_key: "...",
    errors: []
  }
}
```

这说明上传成功时看到 `0` 条风险是正常的中间状态，不应被解释为“合同没有风险”。风险项只有在后续审查任务完成或部分完成后才会写回。

### 2.3 前端导入动作会自动触发审查

`src/App.vue` 的 `startImport()` 调用 `store.importContract()`。`src/stores/review.js` 中的 `importContract()` 顺序为：

```text
electronApi.importContract()
  -> state.value = result.state
  -> 同步本次审查执行快照
  -> 持久化状态
  -> 提示“已导入，开始执行本地审查”
  -> await runReview()
```

`startImport()` 只有在 `store.importContract()` 返回后才执行：

```js
modal.value = null;
activeView.value = "review";
```

这会造成一个重要的界面时序问题：审查执行期间上传弹窗仍然在前台，且“开始审查”按钮处于忙碌状态；审查工作区虽有任务卡，但尚未切换过去，用户无法直接看到规则、检索、模型和校验进度。审查完成、部分完成或失败后才会进入工作区。

## 3. 风险项是如何生成的

`electron/review-runner.cjs` 的 `runReview()` 是风险生成的主编排器，当前顺序如下：

```text
检查合同解析文本
  -> 读取本次规则、企业制度和已发布法律快照
  -> 将知识条款转换为确定性规则
  -> 执行确定性规则
  -> 用关键词重叠检索法律/制度依据
  -> 给规则结果附加依据
  -> 选择 analysis 模型
  -> 将合同文本和依据发送给模型
  -> 解析、归一化模型 JSON 风险
  -> 合并重复风险
  -> 写入 review.risks
  -> 更新任务状态和错误列表
  -> 生成 Validator 结果
```

### 3.1 确定性规则风险

规则来源是本次审查勾选的规则文件。`rulesFromKnowledge()` 会把知识条款或显式规则转成可执行规则，当前支持的主要类型包括：

- `amount_ratio`：抽取付款、预付款或首付款比例，与阈值比较；
- `required_clause`：检查必需条款关键词是否存在；
- `date_order`：检查两个日期相关文本的位置顺序；
- `keyword`：检查关键词是否出现在合同文本中。

规则执行函数 `evaluateDeterministicRules()` 会生成统一风险对象。即使合同中没有找到所需文本，也可能产生一个 `needs_verification` / `unverified` 的待核验结果，用来表达“当前文本不足以判断”，而不是把缺少事实误判为无风险。

规则结果通常包含：

```text
source_type=deterministic_rule
rule_id=规则标识
risk_level=critical/high/medium/low/info
title=规则标题
contract_location=页码、条款号、原文片段
conclusion_status=candidate/rejected/needs_verification
evidence_status=verified/unverified
```

### 3.2 法律和企业制度依据

规则结果会经过 `attachEvidence()`。当前检索源包括：

- 已选且已发布的企业制度；
- 当前审查配置绑定的、状态为 `published` 的法律快照。

`electron/knowledge.cjs` 的 `searchKnowledgeSources()` 当前使用标题、条款正文和关键词的中文分词重叠计算分数，再按分数排序截取有限结果。它不是 Embeddings 向量检索，也没有 RRF、实体图或 Cross-Encoder 重排。

检索结果会被放入风险对象的两个字段：

```text
legal_basis    -> 法律快照中的文件、条款、原文摘录和快照 ID
company_basis  -> 企业制度或其他企业资料中的文件、条款和原文摘录
```

如果至少有一条法律或企业依据，当前编排会把有依据的规则结果标记为 `evidence_status=verified`。这只是“已有来源依据”的工程状态，不等同于法务已经确认风险结论。

### 3.3 analysis 模型风险

如果 `executionModel()` 找到可用的 `analysis` 模型，编排器会调用 `services.invokeModel()` 或默认的 `invokeModel()`。模型请求包括：

- 合同类型；
- 合同解析文本，当前截取前 60,000 个字符；
- 已检索的法律和企业制度条款；
- 系统提示，要求只返回 `{"risks": [...]}` JSON，并要求无明确原文依据的结论使用 `needs_verification` 和 `unverified`。

模型网关会：

1. 构造 OpenAI 兼容的 `/chat/completions` 地址；
2. 通过凭据引用从主进程读取凭据；
3. 发送 `response_format: { type: "json_object" }`；
4. 按模型配置执行超时和有限重试；
5. 解析响应中的结构化 JSON；
6. 将 HTTP 错误、超时、非法 JSON 和配置错误归一化为错误码。

模型输出通过 `normalizeModelRisks()` 归一化：

- 强制 `source_type=model_analysis`；
- 校正风险等级、类别、结论和证据状态枚举；
- 依据引用的原文片段重新计算页码和条款定位；
- 默认 `human_status=pending_review`；
- 模型声称 `confirmed` 但证据不是 `verified` 时，不允许直接成为确认结论；
- 非法或无法解析的输出会生成“模型输出无法解析，需人工核验”的证据风险，或由网关返回 `MODEL_OUTPUT_INVALID`。

模型风险不是最终法律结论。它们必须经过人工处理，并受到 Validator 导出门禁约束。

### 3.4 风险合并

规则风险和模型风险通过 `mergeReviewFindings()` 合并。当前主要以“页码 + 条款号 + 标题”或相同标题判断重复：

- 不重复的风险分别保留；
- 重复风险合并法律依据和企业依据；
- 任一路径证据为 `verified` 时，合并结果可升级为 `verified`；
- 已有 `needs_verification` 时，若另一结果有更明确结论，会使用后者，但仍受统一枚举和人工状态约束；
- 多个来源会在 `evidence_origin` 中留下组合标记。

最终结果通过：

```js
review.risks = mergeReviewFindings(findings);
```

并随审查版本和任务状态一起保存。

## 4. 风险数据落点和前端绑定

### 4.1 Electron 持久化

`review:run` IPC 处理器调用 `runReview()`，然后将结果写回：

```js
reviews: {
  ...stored.reviews,
  [projectId]: result.review
}
```

同一动作还会写入审计记录，记录“执行合同审查”、任务状态以及风险数量。前端随后收到包含 `state` 的结果，并将它设置为 Pinia 状态。

### 4.2 Pinia 状态

`src/stores/review.js` 的数据关系是：

```js
const activeProject = ...;
const review = computed(() =>
  activeProject.value
    ? state.value.reviews[activeProject.value.project_id] || null
    : null
);
const risks = computed(() => review.value?.risks || []);
```

因此前端风险列表的唯一主来源是当前活动项目的 `review.risks`。模型配置、合同文件对象、审计记录和 Dashboard 的历史示例数据都不是当前风险清单的主数据源。

### 4.3 Dashboard

`DashboardView.vue` 使用 `store.risks.length` 展示：

- 首页文案中的“已生成 X 条结构化风险”；
- “发现风险”统计卡片；
- `critical/high` 数量；
- 当前活动任务的风险数量和高风险数量。

Dashboard 的活动任务同时读取 `store.review.task.status` 和 `store.review.task.progress`。但任务状态的代码口径存在兼容差异：审查运行器使用 `running`，Dashboard 历史任务和颜色映射主要使用 `working`。审查完成后通常会变成 `completed`，问题主要出现在运行中状态的标签和样式表现。

### 4.4 ReviewWorkspace

进入 `ReviewWorkspace.vue` 后，用户可看到：

- 顶部“本次审查执行配置”，包括 analysis、extraction、embedding、rerank 和 Skill 数量；
- “审查任务”卡片，包括状态、说明、进度条、当前步骤和错误码；
- 合同原文和页级定位；
- “风险清单”及风险数量；
- 按 `critical/high/medium/low` 筛选；
- 每条风险的等级、类别、标题、页码、条款号、证据状态和人工处理状态；
- 风险详情中的合同原文、风险分析、修改建议、法律依据、企业制度与资料依据。

点击风险会调用 `store.selectRisk()`，把 `activeRiskId` 设置为风险 ID，并同步跳转到风险定位页码。

空列表时当前固定显示：

```text
暂时没有风险项
导入合同并完成审查后，风险会显示在这里。
```

这句文案没有区分“仍在执行”“无规则命中”“模型未配置”“模型调用失败”“合同解析为空”和“确实没有候选风险”，因此很容易造成“风险功能没有体现”的判断。

## 5. 典型成功场景

以采购合同预付款比例为例：

```text
合同正文：预付款 40%
企业制度：预付款比例不得超过 30%
法律快照：已发布并已绑定
analysis 模型：active，校验通过，凭据可用
```

预期链路：

1. DOCX/PDF 解析得到带页码的文本；
2. 规则库条款被转换为 `amount_ratio` 规则；
3. 规则抽取到 `40%`，与 `30%` 阈值比较并产生候选风险；
4. 企业制度和法律快照检索命中，风险补充具体文件、条款和摘录；
5. analysis 模型根据合同文本和依据补充模型风险；
6. 同页同条款同标题的结果被合并；
7. `review.risks` 写回当前项目；
8. Dashboard 显示风险数量；
9. ReviewWorkspace 显示风险卡片，点击后可定位到合同原文；
10. 高风险仍为待人工确认，未完成人工处理前不能直接通过导出门禁。

当前仓库中的 `test/p0-engine.test.cjs` 已覆盖一个不配置模型、仅依赖规则和企业制度生成风险的场景：规则结果可以完成，且依据包含文件名、条款号和 `30%` 原文摘录。这证明规则和知识依据路径可独立产出风险，不依赖模型调用成功。

## 6. 为什么用户可能看不到风险项

### 6.1 上传阶段的正常空列表

`contract:import` 明确初始化 `risks: []`。如果用户在任务完成前查看某个统计或缓存状态，数量为 0 属于正常中间状态。

### 6.2 审查过程被上传弹窗遮挡

`startImport()` 等待 `store.importContract()` 完整返回，而 `importContract()` 又等待 `runReview()` 完整返回。因而规则执行、知识检索、模型请求和重试过程都没有在审查工作区实时可见。

### 6.3 模型配置保存了，但没有进入执行选择

以下任一情况都会导致模型不被使用：

- 角色不是 `analysis`；
- 状态仍为草稿或已停用；
- 未通过校验，聊天入口会将其排除；
- 模型标识或 API 地址为空；
- 凭据引用没有本机对应凭据；
- 当前审查的执行快照仍绑定旧模型或空模型；
- API 地址、模型标识或服务商参数不符合兼容接口要求。

没有可用 analysis 模型时，系统仍会执行规则和知识依据路径，但不会产生模型风险。若规则也没有命中，最终风险可能为 0。

### 6.4 没有启用规则、制度或已发布法律快照

导入阶段会根据当前工作区选择项绑定配置。如果没有选中的有效规则，确定性规则不会产生结果；如果没有已发布快照或制度，规则结果缺少依据，甚至可能无法形成可导出的完整风险。知识文件为草稿、解析失败或 `selected=false` 时也会被跳过。

### 6.5 合同文本无法解析

当 `review.project.file_version_id` 缺失或 `review.document.text` 为空，任务直接进入：

```text
status=failed
current_step=parse
error=DOCUMENT_TEXT_UNAVAILABLE
```

扫描 PDF 在 OCR 不可用时可能只有文件元数据而没有可靠文本层，属于当前已知边界。此时不会因为文件上传成功就自动产生有效风险。

### 6.6 模型请求失败或返回非法内容

模型网关可能返回：

| 错误码 | 常见原因 | 结果 |
|---|---|---|
| `MODEL_CONFIG_INVALID` | 模型标识、地址或凭据引用无效 | 不产生模型风险，保留已有规则结果 |
| `MODEL_REQUEST_FAILED` | HTTP 错误、网络错误、超时或重试耗尽 | 任务通常为 `partial`，规则结果保留 |
| `MODEL_OUTPUT_INVALID` | 返回内容不是可解析 JSON | 不能当作已确认结论，需人工核验或重试 |
| `MODEL_REQUEST_CANCELLED` | 请求被取消 | 当前结果按取消路径处理，不应伪造完成 |

在 `runReview()` 中，模型失败会追加到 `review.task.errors`，最终任务状态变为 `partial`；已有规则结果不会被删除。当前界面虽然在任务卡显示错误码和消息，但只有进入审查工作区后才能看到，上传执行期间不易发现。

### 6.7 过滤条件把风险隐藏

风险清单支持按等级筛选。如果用户停留在 `critical` 或 `high` 等级，而当前结果只有 `medium` 或 `low`，列表会显示空状态。空状态没有同时显示“当前筛选条件下 0 条、全部等级共 X 条”，容易误判为没有风险。

### 6.8 活动项目和展示状态不一致

Pinia 只展示 `activeProjectId` 对应项目的风险。如果状态加载后活动项目切换、审查结果尚未写回，或者用户查看的是历史任务的静态示例行，页面上会出现任务存在但当前风险数量为 0 的情况。排查时必须先确认 `activeProjectId`、`project_id` 和 `state.reviews[projectId]` 一致。

## 7. 当前界面已经体现和仍未体现的内容

| 用户问题 | 当前已有表现 | 当前不足 |
|---|---|---|
| 模型是否参与本次审查 | 工作区显示执行配置和模型名称 | 上传执行期间不可见；未显示“实际调用/未调用”结果 |
| 审查是否正在进行 | 工作区有任务状态和进度 | 上传弹窗等待期间看不到；`running/working` 口径不一致 |
| 风险有多少条 | Dashboard 统计、任务表风险列、风险清单数量 | 空结果没有原因分类 |
| 风险从哪里来 | 风险对象有 `source_type`，详情显示依据 | 卡片没有直接显示“规则/模型/规则+模型”来源 |
| 为什么没有模型风险 | 任务错误区可能显示错误码 | 没有在结果摘要中说明“规则结果保留、模型路径失败” |
| 风险是否可信 | 证据状态、人工状态和详情依据 | 用户不容易理解 `candidate`、`needs_verification` 和 `verified` 的区别 |
| 能否定位原文 | 风险详情显示页码、条款号、摘录并联动页码 | 扫描 PDF/OCR 不可用时缺少明确的下一步处理提示 |
| 是否可以导出 | Validator 和导出门禁已实现 | 用户需要先打开导出流程才能知道哪些风险阻断导出 |

## 8. 建议的界面闭环改进

本节是产品和实现建议，不代表当前代码已经完成。

### 8.1 上传后立即进入“审查执行中”页面

`contract:import` 成功后立即关闭上传弹窗并切换到 ReviewWorkspace，保留任务状态为 `queued/running`。`runReview()` 在后台执行，前端通过已有 `onReviewProgress` 订阅更新任务卡。这样用户可以看到：

```text
解析合同  -> 执行规则  -> 检索依据  -> 调用模型  -> 校验  -> 保存
```

完成后风险清单自动刷新，不需要用户猜测是否仍在执行。

### 8.2 增加结果摘要条

在风险清单标题附近显示：

```text
共生成 8 条候选风险：规则 3 条 · 模型 5 条 · 高风险 2 条 · 待人工确认 6 条
```

摘要应来自实际 `review.risks`，不要从模型原始文本或示例数据推断。

### 8.3 显示风险来源

风险卡片可以增加来源标签：

- `确定性规则`；
- `analysis 模型`；
- `规则 + 模型合并`；
- `局部审查`；
- `人工新增`。

标签应基于 `source_type` 和 `evidence_origin`，并在详情中说明来源不是法律结论。

### 8.4 将空状态拆成可行动状态

至少区分以下状态：

| 状态 | 页面提示 | 建议操作 |
|---|---|---|
| `queued/running` | “审查进行中，风险结果尚未最终生成” | 查看任务步骤或取消/等待 |
| `completed` 且 0 条 | “本次规则和模型未发现候选风险” | 查看执行配置、规则范围和原文 |
| `partial` | “模型路径失败，已保留 X 条规则风险” | 查看错误码并重试 |
| `failed` + `DOCUMENT_TEXT_UNAVAILABLE` | “合同没有可用解析文本” | 更换可搜索文件或配置 OCR |
| 没有可用模型 | “未调用模型，仅执行规则路径” | 配置并启用 analysis 模型 |
| 当前筛选为空 | “当前等级无风险，全部等级共 X 条” | 清除等级筛选 |

### 8.5 让配置结果进入审查结果

任务卡应显示本次实际执行快照，而不仅是当前能力配置列表：

- analysis 模型名称、模型标识和配置版本；
- 实际调用状态、耗时和重试次数；
- 规则文件、企业制度和法律快照版本；
- 模型错误码和降级路径；
- 风险来源计数。

这样可以直接回答“我配置的模型是否真的参与了这次审查”。

### 8.6 统一任务状态枚举

阶段契约文档已将任务运行态收口为统一口径，但当前运行器仍使用 `running`，Dashboard 历史数据使用 `working`。后续应统一状态值、显示标签和颜色映射，并为状态变化补充自动化测试。该问题不会直接生成风险，但会影响用户对“任务是否完成、是否可以查看风险”的判断。

### 9.4 故障注入验证

| 场景 | 预期任务状态 | 预期风险结果 | 预期界面信息 |
|---|---|---|---|
| analysis 模型停用 | `completed` 或规则路径结果 | 只保留规则风险，可能为 0 | 明确提示未调用模型 |
| 凭据引用不存在 | `partial` | 规则风险保留，模型风险为 0 | `MODEL_CONFIG_INVALID` |
| API 返回 401/403/500 | `partial` | 规则风险保留 | `MODEL_REQUEST_FAILED`，错误脱敏 |
| 请求超时 | `partial` | 规则风险保留 | 显示重试耗尽或超时 |
| 模型返回非 JSON | `partial` 或规范化待核验风险 | 不得形成确认结论 | `MODEL_OUTPUT_INVALID` |
| 扫描 PDF 无文本 | `failed` | 风险为空 | `DOCUMENT_TEXT_UNAVAILABLE`，提示 OCR/可搜索文件 |
| 未勾选规则和制度 | `completed` | 可能为 0 | 提示本次没有有效规则或知识依据 |
| 仅筛选高风险但只有中风险 | `completed` | 全部风险仍在数据中 | 显示筛选后 0 条、全部共 X 条 |

### 9.5 通过标准

本功能链路可判定为“当前实现通过”的最低标准：

1. 合同导入后创建独立项目、文件版本和审查任务，初始 `risks=[]` 可解释。
2. `review:run` 能在至少一个合同类型上用规则和知识依据生成结构化风险。
3. analysis 模型可用时，模型 JSON 能进入统一风险 Schema，并与规则结果合并。
4. 模型失败时不丢失已有规则结果，不产生未经依据的确认结论。
5. 风险写入 `state.reviews[projectId].risks`，刷新或重新加载后仍能显示。
6. ReviewWorkspace 能展示风险卡片、定位、依据和人工处理状态。
7. Dashboard 风险统计与当前项目 `review.risks` 一致。
8. Validator 能阻断未人工复核、无定位或无有效依据的不可导出结果。

## 10. 当前边界和后续任务

### 已实现

- 合同上传、原始文件版本化和 DOCX/PDF 基础解析；
- 规则执行、企业制度和法律快照的关键词检索；
- OpenAI 兼容 analysis 模型调用、JSON 解析、有限重试和错误码；
- 规则风险与模型风险的归一化、去重和依据合并；
- 风险持久化、任务进度、审查工作区和 Dashboard 统计；
- 风险详情、原文定位、人工处理和导出门禁。

### 部分实现或未实现

- 上传执行期间的实时结果可见性不完整；
- 空结果没有按原因分类；
- 模型实际调用摘要没有在结果卡片中充分呈现；
- `running` 与 `working` 状态命名尚未完全统一；
- 当前知识检索仍是关键词重叠，不是向量 + 关键词 + 实体/图信号的混合检索；
- Embeddings API、向量索引、RRF 和 Cross-Encoder 尚未接入当前风险生成主链路；
- 扫描 PDF 的 OCR 和可靠坐标定位尚未完成；
- 完整的任务恢复、Checkpoint 重放和生产级幂等仍属于 M3 后续工作。

## 12. 最终判断

当前系统不是“没有风险生成能力”，而是风险生成结果的用户可见链路不够连续：

```text
已有后端能力：上传 -> 审查编排 -> 风险归一化 -> 持久化 -> 清单展示
当前产品缺口：上传期间反馈 -> 生成来源解释 -> 空结果分类 -> 失败恢复引导
```

用户配置模型后，正确的理解应是：模型在合同导入后由审查任务选中，接收合同解析文本和已检索依据，返回结构化候选风险；系统再将它与确定性规则结果合并，保存到当前项目的 `review.risks`，最后由 ReviewWorkspace 展示并等待人工复核。下一步应优先收口上传后的任务可见性、结果来源摘要和空/失败状态分类，再进行向量检索、RRF 和 Cross-Encoder 等记忆检索能力建设，避免在界面尚未能解释现有结果时继续扩大模型链路。
