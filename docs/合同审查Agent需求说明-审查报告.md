## 0. 结论摘要（TL;DR）

1. 这是一份**成熟度较高的"产品范围 + 设计原则说明"**，在系统边界、证据链、可恢复执行、模型治理、安全防护等"理念层"明显优于一般需求文档。
2. 但它**尚不是一份可直接开发、并据此判定验收通过/不通过的需求规格（SRS）**。短板高度集中，缺四样东西：
   - **量化合格线**：质量/性能指标只有名称，没有目标阈值与发布门禁数值；
   - **可判定的验收用例与需求追踪**：验收用例是流程脚本而非 pass/fail 用例，大量核心需求无编号；
   - **完整契约**：数据模型、工具 I/O Schema、错误码、状态机转移规则缺失或互相矛盾；
   - **两个核心输入依赖的交付定义**：版本化法律知识快照、确定性规则库"从哪来、长什么样、V1 覆盖多少"未定义。
3. 上述差距**不需要推翻现有理念**，主要是补表、补枚举、补状态转移、重写验收用例。按第 8 章路线图补齐后可达到可开发、可验收水平。

## 1. 审查方法与边界

### 1.1 审查维度（八维）

| 维度 | 含义 |
|---|---|
| 范围与边界 | 在范围/不在范围是否清晰，系统能力边界是否明确 |
| 功能覆盖 | 业务功能是否覆盖主要场景、有无关键功能遗漏 |
| 需求可测性 | 每条需求是否无歧义、可测量、可被一条测试验证 |
| 数据/接口契约 | 数据对象、字段、枚举、工具输入输出、错误码是否完整到可实现 |
| 状态机可实现 | 状态、状态转移、异常路径、幂等是否定义到可编码 |
| 非功能量化 | 性能、容量、可靠性、兼容、部署是否有可验收的量化标准 |
| 验收用例可判定 | 验收用例是否有确定输入、可核对的预期输出与通过准则 |
| 安全合规设计 | 权限、注入防御、数据保护、密钥安全是否可落地、可测试 |

### 1.2 检查边界声明

- 本报告评估的是**需求文档本身的可验收性**，不替代法律专业内容审校，也未对文中引用的外部法规、外部文章（`ai-capability-engineering` 系列）做事实核验。
- 报告中给出的指标建议值、模板示例属于**方法学建议与待确认占位**，最终阈值须由法务、业务与研发结合自身风险偏好确定，不代表已查证的既定标准。
- 章节号、FR 编号、字段名引用均以被审文档 v0.3 原文为准。

## 2. 总体评价

### 2.1 定位判断

文档在"想做什么、不做什么、坚持什么原则"层面表达清楚且专业：明确不替代律师、不自动签署/发送/付款、离线可运行、法律来源 L1–L5 分级、区分"合同签订日对应法律版本"与"当前审查日有效版本"、强调证据绑定与人工复核、模型配置与法律来源解耦、密钥不落明文、人工纠正不直接上线。这些是构建可信合同审查系统的正确前提。

问题集中在**从"原则"到"可判定契约"的最后一公里**：文档大量使用"应、尽量、必要时、高风险、代表性、有限重试"等需要实现者二次解释的表述，且缺少把这些表述钉死成数值、枚举、转移条件和预期结果的配套定义。其结果是——不同团队会做出不同理解，验收时无法客观判定是否达标。

### 2.2 八维成熟度评分（评审评估，满分 10）

| 维度 | 评分 | 评价 |
|---|---|---|
| 范围与边界 | 9 | 在/不在范围、三种资料模式、P0/P1、产品边界总结清晰 |
| 功能覆盖 | 8 | 场景与功能覆盖广，五类合同专项较细 |
| 需求可测性 | 4 | 模糊限定词多，风险分级/置信度/阈值无定义 |
| 数据/接口契约 | 3 | 仅 1 个 JSON 示例且自相矛盾，对象无字段级定义，工具无 Schema、无错误码表 |
| 状态机可实现 | 4 | 有状态枚举无转移规则，存在幽灵状态 |
| 非功能量化 | 2 | 只有指标名与"记录 P50/P95"，无目标值、容量与部署标准 |
| 验收用例可判定 | 3 | 13 条 AC 为流程描述，无确定输入/预期输出/通过准则 |
| 安全合规设计 | 6 | 原则全面，但沙箱规格、加密强度、失败策略、注入通过率缺验收标准 |
| **综合（平均）** | **4.9** | 理念强、契约弱，尚不足以直接支撑开发验收 |

当前文档状态：
  范围/原则充分  ✓✓✓
  可测需求       △（部分有编号，大量散文）
  处理契约       ✗（Schema/错误码/状态转移缺失，示例矛盾）

## 3. 阻断级问题（Blocker，共 5 项）

> 判定标准：不补齐则无法客观判定"验收通过"，或会在联调/验收阶段必然返工。

### B1 质量与性能指标只有名称、没有合格阈值，发布门禁无数值红线

- **位置**：17.2 核心指标（20 项）、17.3 发布门禁、16.2 性能。
- **问题**：17.2 列出风险召回率、高风险漏报率、误报率、定位准确率、结构化输出通过率等 20 个指标，但**没有一个给出目标值或最低可接受值**；17.3 仅要求"检查是否恶化""不能仅凭总体通过率上线"，未定义何为恶化、何为达标。16.2 要求"记录 P50/P95"但未给目标。
- **后果**：验收时高风险漏报率做到 5% 还是 30% 算通过、局部审查 P95 是 3 秒还是 30 秒，均无判据，验收必然变成主观争论。
- **整改要求**：
  1. 为每个指标补「定义/计算公式/目标值/最低可接受值/测量样本集/统计口径/对应 AC」七列（模板见附录 A）；
  2. 区分 **P0 必达门禁项**（如高风险漏报、虚构法条、越权、结构化输出）与**观测项**；
  3. 17.3 为每个门禁项给出可执行的数值判定与"恶化"的最小显著差异阈值。
- **完成判定**：任一新版本/模型/规则/Skill 发布时，可仅凭该表与回归报告机械判定"放行/阻断"，无需会议主观解释。

### B2 第 19 章验收用例是流程演示脚本，不是可判定用例

- **位置**：AC-001 ~ AC-013。
- **问题**：13 条用例全部以"系统完成……""用户可以……"描述，缺少：确定的前置数据规格（合同页数、条款数、预置的制度包与法律快照版本）、确定输入、**可核对的预期输出**（应发现哪几类风险、至少几条、定位到什么精度）、通过/失败判定准则。例如 AC-001"每条风险均能定位到页码、条款号和原文"，未定义"页码正确但条款号偏差""字符范围偏移 N 字符"是否算通过。
- **后果**：测试执行人无法判对错，同一用例不同人结论不同。
- **整改要求**：用 Given-When-Then 模板重写全部 AC（模板与 AC-001 改写样例见附录 C），每条 AC 必须绑定对应 FR 编号与至少一个 17.2 指标；明确数据夹具（fixture）、操作步骤、预期结果、容差与失败归类。
- **完成判定**：任意一条 AC 都能由不参与开发的测试人员独立执行并给出唯一的通过/不通过结论。

### B3 大量核心功能没有需求编号，无法做需求覆盖与追踪

- **位置**：带编号 FR 仅见于 7.1、7.2、7.3、7.4、7.11；而 **7.5 辅助资料、7.6 五类合同审查范围、7.7 法律知识库、7.8 风险识别、7.9 人工纠正、7.10 导出、第 8 章 Skill、第 10 章 Memory、第 11~13 章**基本为散文或清单，无唯一需求编号。
- **问题**：无法建立"需求 ↔ 用例 ↔ 指标"的需求追踪矩阵（RTM），也就无法证明每条需求都被测试覆盖、无法评估变更影响面。
- **整改要求**：将所有需求拆解并编号到"一条只表达一个可验证断言"的粒度（避免一条 FR 内含多个可独立失败的断言），并建立 RTM（模板见附录 B）。
- **完成判定**：RTM 中不存在"无任何 AC 覆盖"的需求，也不存在"找不到对应需求"的 AC。

### B4 核心输入依赖"法律知识快照"与"确定性规则库"无交付定义

- **位置**：3.3 混合审查链路、7.7 法律知识库、9.3 `legal.snapshot_search` / `rule.evaluate`、P0（第 18 章）。
- **问题**：标准审查模式与整条链路都依赖"版本化法律知识快照"和"确定性规则检查"，但全文未定义：
  - 初始快照由谁提供、**V1 覆盖的最小法规清单**（名称/文号/版本）、数据 Schema 与目录结构、同步与版本流程；
  - 规则库中规则的**表达形式**（DSL / 配置 / 代码）、V1 内置规则清单、规则版本化方式；
  - **规则（rule.evaluate）与 Skill 内规则的职责边界**（两者都做"检查"，易重叠冲突）。
- **后果**：这是输入侧地基。不定义则系统即便开发完成也"无米下锅"，审查质量无法验收，且最可能在联调后期才暴露数据缺口。
- **整改要求**：交付四份定义——①V1 法规清单与快照 Schema；②快照生产/更新/版本/回滚流程；③规则目录（规则 ID、触发条件、输出、适用合同类型、优先级）；④规则与 Skill 的分工原则。两者均需各自验收用例。
- **完成判定**：可基于一份明确的法规/规则清单独立验收"快照检索"和"规则命中"，不依赖实现者口头说明。

### B5 三套状态机只有状态枚举、没有转移规则，且存在幽灵状态

- **位置**：11.1 任务状态、7.11.5 模型配置状态、8.6 Skill 状态、11.3 Checkpoint 恢复。
- **问题**：
  - 三处均只列状态与释义，**缺"现态 → 触发事件 → 守卫条件 → 次态 → 动作 → 是否可逆"的转移表**，异常路径（本系统重点）无法实现与测试；
  - 11.3 出现 `input_received`，但 11.1 的状态集合中**不存在该状态（幽灵状态）**；
  - 模型侧 `testing` 失败后无对应失败态：`unhealthy` 是运行期健康态，语义不符；Skill 侧有 `validation_failed`，模型侧却缺 `test_failed` 一类状态。
- **整改要求**：补三张状态转移表/图（模板见附录 D），明确合法/非法转移及非法转移处理；删除或补登 `input_received`；模型侧补测试失败态。
- **完成判定**：任意"状态 + 事件"组合都能在表中查到唯一确定的次态与动作，未定义组合有明确拒绝策略。

## 4. 重要级问题（Major，共 7 项）

> 判定标准：不阻断立项，但会导致实现分歧、返工或验收扯皮，应在开发前澄清。

### C1 风险字段语义自相矛盾，关键枚举与置信度无定义

- **位置**：7.8 风险类型表与同节 JSON 示例。
- **问题**：7.8 将 `risk_type` 定义为五大类（法律/商业/公司制度/文本质量/证据），但同一 JSON 示例却取 `"违约责任"`（属具体主题，不在五类内），字段语义自相矛盾。`risk_level`、`evidence_status`、`human_status` 未给枚举集；`confidence=0.82`、`location_confidence=0.96` 未给取值范围、计算方法与分档阈值；"高风险""低置信度"因此无法判定。
- **整改**：拆分为 `risk_category`（五分类枚举）+ `risk_topic`（具体主题）；产出全局字段/枚举字典，定义风险评级矩阵与置信度分档及对应动作（如低于阈值强制降级为"待核验"）。

### C2 模型角色三处口径不一致，视觉/OCR 边界未定

- **位置**：FR-071、7.11.2 配置项 `model_role`、7.11.2 四类角色说明、7.11.2 末段。
- **问题**：FR-071 列"对话分析/结构化抽取/Embedding/Rerank"；7.11.2 配置表多出"视觉理解"；其下又只要求 analysis/extraction/embedding/rerank 四类；末段又称 OCR/版面解析可走本地服务。视觉模型是否属于 V1、扫描件理解走模型 API 还是本地服务，三处需统一。
- **整改**：给出唯一的 `model_role` 枚举与 V1 范围说明，明确 OCR/版面/视觉的实现通道与边界。

### C3 数据模型与 MCP 工具契约太薄，错误码体系缺失

- **位置**：第 15 章数据对象、9.3 MCP 能力、11.4 错误处理。
- **问题**：第 15 章 21 个对象仅列字段名片段，无数据类型、必填、长度/格式、主外键、唯一约束、级联与索引，无法直接建库或定接口。9.3 要求每个工具"必须有明确输入/输出 Schema、错误码、超时、重试策略、幂等键"，但正文没有任何一个工具给出 Schema，**全文也无统一错误码表**（11.4 只有处理策略，无 `error_code` 枚举与错误响应结构）。
- **整改**：补 ER 关系与字段级定义；逐工具给出 I/O Schema、默认超时/重试/幂等键规则；建立统一错误码目录（码、含义、是否可重试、对应状态迁移、对外提示）。

### C4 大量需求使用不可测的模糊限定词

- **位置**：全文，典型如下。

| 表述 | 位置 | 需替换为 |
|---|---|---|
| "尽量保持原始页面布局" | FR-021 | 可量化的版式保真要求或明确降级标准 |
| "前后必要上下文" | FR-034/FR-035 | 默认上下文窗口规则（条款级/N 句/可配）与扩圈条件 |
| "高风险/高额金额/重大责任" | 12 高风险处理 | 风险评级矩阵与金额/责任分档阈值 |
| "低置信度"、OCR 可用性 | FR-015/FR-017 | 置信度阈值、低于阈值的状态与处理 |
| "有限重试""不得无限重试" | 7.11.6/11.4 | 默认最大次数、退避算法、不可重试错误清单 |
| "代表性 Eval/非敏感样例" | 8.5/7.11.4 | 样例集构成、覆盖类别与合格标准 |
| "普通 PDF/大文件/长文本/复杂表格" | 16.2 等 | 页数/大小/单元格规模的明确界定 |
| "最小必要脱敏" | 13.3/13.4 | 敏感字段清单、脱敏算法与"保留定位绑定"的规则 |

- **整改**：逐词替换为可测量定义或"带默认值、可配置"的参数，并在字段字典中登记。

### C5 "单人工作台"与多角色/多层级/数据隔离存在定位张力，权限矩阵缺失

- **位置**：3.1/4.1（单人、不协同）对比 5.1（三角色）、7.11.3（系统>组织>类型>项目>任务五级绑定）、8.7（组织级/用户级作用域）、FR-001（个人数据隔离）、第 15 章 User/组织字段。
- **问题**：需明确到底是"单会话不协同的多账号单租户系统"还是"纯单机单用户系统"——这决定是否需要账号体系、组织模型、并发控制与隔离强度，并直接影响架构与验收规模。同时**缺少一张"角色 × 功能 × 数据"的权限矩阵**（设计依据中引用了 `permission-matrix.md`，正文却未产出该矩阵），认证方式（账号密码/SSO/LDAP）也未定义。
- **整改**：用一段定死部署与账号模型；补权限矩阵（每角色对每功能/数据对象的读/写/管权限）与认证方式、会话策略。

### C6 P0 范围等同完整产品，不是 MVP，缺阶段性验收点

- **位置**：第 18 章 P0。
- **问题**：P0 同时包含五类专项审查、Skill 全生命周期（含沙箱内运行代表性 Eval、升级/回滚）、模型配置九状态与多角色及受控降级、可选实时核验、四种导出、七层 Memory、全套 Trace/Checkpoint/Validator。这在工程量上接近 V1.0+，且只有一个巨型验收节点，中途无法证伪。
- **整改**：切分为可独立验收的里程碑，例如：
  - **M0 最小闭环**：导入解析 + 阅读器定位 + 通用规则检查 + 人工划词 + 一种导出；
  - **M1 专项与知识**：五类专项 + 法律快照 + 整份审查 + 人工纠正沉淀；
  - **M2 治理与增强**：模型治理、Skill 治理、实时核验与降级、其余导出格式。
  每个里程碑绑定各自的指标门禁与 AC 子集。

### C7 非功能需求缺量化，运行/部署环境缺失

- **位置**：第 16 章、第 14 章。
- **问题**：16.2 仅要求"记录 P50/P95"而无目标值，"局部审查优先于整份审查"为定性描述；文件大小、页数、项目数、并发数仅写"可配置"，无默认值与上限；缺部署形态（B/S 或单机）、浏览器/操作系统兼容矩阵、服务器与本地模型硬件要求、系统自身可靠性（RTO/RPO、备份）、容量上限。
- **整改**：补 NFR 量化表（延迟、吞吐、容量、并发、RTO/RPO）、部署与兼容矩阵、各项配置的默认值与硬上限。

## 7. 值得肯定与保留的设计

以下设计方向正确、专业，**整改时应保留、不应削弱**：

1. **边界克制**：明确辅助定位、不替代律师/法务最终判断；不提供自动签署、外发、付款、外部系统写入工具。
2. **离线可用与来源分级**：不把实时互联网作为唯一运行条件；法律来源 L1–L5 分级，线索（L5）不得单独支撑结论。
3. **法律时间维度**：同时判断"合同签订日对应版本"与"当前审查日有效版本"，历史/当前分别展示，不倒推适用——专业性强。
4. **证据链与可观测**：Trace→Span→Event、Artifact 引用 + SHA-256、原文不灌日志、每条风险可回溯。
5. **可恢复与幂等**：Checkpoint、已完成步骤不重复、重复提交不产生重复副作用。
6. **模型治理**：模型与法律来源解耦、人工配置批准、密钥引用不落明文、受控降级且切换可见可审计、数据出域策略。
7. **人工闭环**：保留 AI 原始结果与人工修订差异，纠正先入候选样本/Golden Set，经回归门禁才更新线上能力。
8. **Skill 受控扩展**：人工安装、隔离校验、作用域与优先级、更具体 Skill 不得降低安全等级。

## 10. 放行结论与建议

- **当前版本（v0.3）结论：有条件暂缓。** 文档可作为需求基线与设计对齐材料，但**不建议直接据此进入开发排期与最终验收**，原因是 5 项阻断级问题使验收缺乏客观判定依据。
- **建议的准入门禁**：B1–B5 五项阻断问题全部关闭（指标有阈值、AC 可判定、需求可追踪、两大输入依赖有交付定义、状态机完整且无幽灵状态），C 类重要问题至少关闭 C1/C2/C3/C5（契约与模型一致性），即可进入开发；其余 C 类与 D 类可在里程碑内并行完善。
- **复核方式**：整改为 v0.4 后，按本报告第 8 章路线图逐项核对，并抽查"任一指标/AC/状态组合是否都能得到唯一确定结论"作为回归检查。

> 本报告为文档可验收性评审，不构成法律意见；附录中的建议阈值为方法学占位，须经业务与法务确认后方可成为正式验收标准。
