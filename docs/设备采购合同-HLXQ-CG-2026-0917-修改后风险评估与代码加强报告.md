## 四、误报、重复和证据问题

### 4.1 明确错检

合同块 `docx_block_17` 的原文是 `1.4 "交货地点"...`，但当前 `clauseDefinitions()` 只接受编号后紧接中文字符，因引号而漏掉 `1.4`。因此：

- `5.1 -> 1.4` 是误报；
- `5.5 -> 6.4` 才是合同中确实没有定义的条款；
- `clauseDefinitions()` 还会从金额小数中产生 `500.00`、`000.00` 等伪条款定义。

这不是模型判断问题，而是确定性解析器问题，应优先修复。

### 4.2 风险重复

当前至少有以下重复主题：

- 含税冲突：`model_3`、`model_19`、`check_GC-2-05`；
- 争议解决：`model_21`、`model_22`、`check_GC-4-19`；
- 金额不一致：`model_2` 与 `check_amount_total_vs_uppercase`；
- 验收：`model_9`、`GC-2-18/19/20`；
- 违约责任：`model_15`、`GC-4-02/03/05`、两个 penalty 确定性检查。

同一问题被拆散后，用户看见的是多条 medium，而不是一个包含全部条款证据和修约动作的高风险组。

### 4.3 证据污染

事实 `fact_10` 的原文是 `13.5 ... 5%`，但其 `source_refs` 同时包含 13.1 和 13.3 中的 `5%` 短引文。原因是短引文通过全合同搜索，不能唯一确定出现位置。该问题会污染后续责任上限、罚则叠加和风险聚合。

## 五、代码层根因与加强方案

### P0-1：定级策略把真实高风险全部压成 medium

**证据位置**：

- `electron/review-engine.cjs:42-74`：只要没有原文定位、`verified` 证据或 `confirmed` 结论，`high/critical` 就被上限到 `medium`。
- `electron/contract-checks.cjs:152-180`：确定性检查即使是 `conflict`，也先根据是否有引用降级；`candidate` 又无法满足 `normalizeFindingSeverity()` 的 `confirmed` 条件。
- `electron/review-engine.cjs:276-285`：模型风险统一改写成 `needs_verification` + `unverified`。

**问题实质**：把“结论置信度”和“合同风险严重度”混为一个字段。金额冲突、全额预付、0.5%/日等问题即使需要人工确认，也不应因尚未 `confirmed` 而变成 medium。

**建议**：

1. 将 `risk_level`（风险影响）与 `decision_confidence`（证据/结论置信度）拆开。
2. 对确定性规则使用矩阵：`conflict + resolved + quote` 保留规则等级；状态为 `candidate` 或 `pending_review`，而不是强制降级。
3. 缺失型检查使用“全文检查范围 + absence_scope + document_hash”作为证据，不要求必须存在正向 quote。
4. 只有模型候选且没有本地证据时才执行 medium 上限。

### P0-2：条款索引没有优先使用解析块的 `clause_no`

**证据位置**：`electron/contract-evidence.cjs:45-64、67-85、114-124`。

当前数字条款正则要求编号后直接出现中文字符，不能识别 `1.4 "交货地点"`；同时把金额小数误认为条款。解析器已经在 `parser.cjs` 中为 DOCX 块提供 `block_id`、`clause_no` 和 `char_range`，但交叉引用检查重新从扁平文本推导条款，造成信息丢失。

**建议**：建立一次性的 `clause_registry`：

- 首选解析块的 `clause_no`、`char_range` 和标题；
- 数字条款标题允许空格、全角空格、引号、括号、冒号等前缀；
- 排除金额、版本号、外部法条和正文中的“第 X 条”引用；
- 对重复的“第九条”保留 `clause_instance_id`，不能只用 `clause_no`；
- 交叉引用按 `clause_instance_id` 解析，最终输出“来源条款、目标条款、目标是否存在”。

### P0-3：跨条款引用没有按边界绑定证据

**证据位置**：`electron/contract-checks.cjs:225-244`。

`extractClauseReferences()` 已经返回 `from_clause_no`、`target_clause_no`、`char_range` 和 `quote`，但当前又用完整上下文 quote 调用 `textRefs()`，完整上下文经常不等于某个块的连续文本，最终 `source_refs=[]`。

**建议**：直接使用引用边的 `char_range` 定位原文块，生成：

```text
reference_edge {
  from_ref: { block_id, clause_no, char_range, quote },
  target_ref: { block_id, clause_no, char_range, quote } | null,
  target_exists: boolean
}
```

目标不存在时，`target_ref` 为空是“缺失证据”的明确表示，不应让来源条款证据也丢失。

### P0-4：事实短引文全合同搜索，导致跨条款错绑

**证据位置**：`electron/contract-facts.cjs:65-70、89-95、146-162`。

`sourceRefs()` 只拿 `rawText` 全合同搜索；对于 `5%`、`10 日` 等短引文，会把多个条款的命中全部挂到一个事实。

**建议**：引用解析顺序固定为：

1. 按事实的 `clause_no` 或模型提供的 `block_id` 限定候选块；
2. 优先用 `quote_start/char_range` 验证连续子串；
3. 只有完整 `raw_text` 唯一命中时才标记 verified；
4. 多次命中时保留 `ambiguous` 和所有候选，不得自动归给一个条款；
5. 除非事实显式标记 `cross_clause=true`，否则 `source_refs[].clause_no` 必须与 `fact.clause_no` 一致。

### P1-1：风险聚合依赖显式键或完全相同的清单集合

**证据位置**：`electron/review-engine.cjs:303-385`。

当前聚合优先级是显式 `aggregation_key`、单一 `rule_id`、完全相同的 checklist 集合，再退回标题和条款号。模型风险往往没有显式键，模型与清单只共享部分 GC 编号，因此同一主题被拆开；反过来，同主题不同条款又缺少稳定隔离。

**建议**：

- 建立 `canonical_issue_id`，例如 `amount.total_consistency`、`tax.price_basis_conflict`、`dispute.forum_conflict`；
- 建立 `checklist_id/rule_id -> canonical_issue_id` 映射；
- 使用共享清单 ID 的图合并或相似度合并，不要求集合完全相等；
- 合并后保留 `source_risk_ids`、`related_rule_ids`、所有条款证据和最严重等级；
- 以条款集合作为隔离条件，避免把不同条款的同名风险误合并；
- 前端展示一个主风险组，展开显示子检查和证据来源。

### P1-2：罚则规则仍是固定编号和单字段启发式

**证据位置**：`electron/contract-checks.cjs:349-395`。

当前 `penaltyByClause` 是单条 Map，叠加逻辑依赖“除按/另按/同时主张”等固定措辞和旧的 8.1/8.3 兼容正则，无法稳定表达本合同 13.1、13.2、13.3、13.5 的关系。因此 13.1 与 13.2 重复救济、13.3 的 1% 上限与 13.5 的 5% 总上限均未形成独立风险。

**建议**：将每项罚则结构化为：

```text
subject, breach_event, rate, rate_base, cap, remedy_type, clause_no, references
```

再按“同一主体 + 同一违约事件”检查：重复救济、费率对称性、独立上限、上限覆盖范围、解除权与损失赔偿能否叠加。

### P1-3：通用清单把正则未命中当成“缺失条款”

**证据位置**：`electron/general-checklist.cjs:88-92、105-130、194-210`。

大量 `GC-2-05/06/07`、`GC-3-06/07/08/11`、`GC-4-03/05/12/13/18/23/24` 的结果来自正则要素不足，往往没有条款引用。它们可作为待核验任务，但不能与确定性冲突使用同一风险列表和同一排序逻辑。

**建议**：将清单结果分为：

- `conflict`：原文出现相互矛盾或不利约定，有原文证据；
- `missing_candidate`：全文扫描未找到必要要素，保留全文范围和扫描规则；
- `unverifiable`：需要外部材料或业务事实，不能推定合同缺陷；
- `not_applicable`：有明确适用条件未触发。

`missing_candidate` 必须显示“扫描范围、命中的相邻条款、缺失字段”，而不是只有“约定要素待补齐”。

### P1-4：模型输出协议仍不足以保证条款证据

**证据位置**：

- `electron/review-runner.cjs:245、251-254`：提示词只口头要求引用原文，payload 没有结构化证据目录；
- `electron/review-runner.cjs:713-714`：JSON Schema 只约束 `risks` 是数组；
- `electron/review-engine.cjs:262-289`：最终只读取模型风险中的 `contract_location`、`quote`、`char_range`，缺字段不会被拒绝。

**建议**：模型输入提供 `evidence_catalog`（`block_id、clause_no、char_range、text`），输出 Schema 强制每个风险包含：

```text
title, risk_level, conclusion_status,
contract_location: {
  block_id, clause_no, char_range, quote
}, checklist_ids, analysis, suggestion
```

本地必须验证 quote 是指定 block 的连续子串、char_range 与 quote 一致、clause_no 与 block 元数据一致；无法定位时必须填写 `unresolved_reason`，不能静默生成无证据风险。
