# 合同风险漏检根因分析与改进方案

> 文档日期：2026-09-16  
> 分析对象：`合同审批/data/软件采购合同.docx`、`合同审批/data/软件采购合同.pdf`、`合同审批/data/风险清单.md`  
> 目的：解释当前审查功能为什么没有识别测试合同中的真实风险，并提出可实施的改造方案。  
> 实施状态（2026-09-16）：本轮已完成阶段一至阶段三的核心改造，并用 `软件采购合同.docx` 与 `软件采购合同.pdf` 做了端到端回归。本文保留原始根因分析，同时在第 12 节记录已落地能力与尚未交付的能力；“已实现”不等于已经覆盖全部 26 个缺陷的最终评分目标。

## 1. 结论摘要

这次漏检不是单一的“原始合同解析失败”，也不能靠再写一个更长的语义提示词解决。结论分为三层：

1. **原文事实大部分已经进入系统。** PDF 有可搜索文本层，DOCX 的正文、金额、百分比、条款号和附件表格内容都能被抽取。26 个真实缺陷所依赖的关键字面事实在解析结果中基本存在。
2. **解析器存在结构性损失。** DOCX 当前使用 `mammoth.extractRawText()`，把文档压成 1 个“页面”，并把 6 个表格展平为线性文本；PDF 当前只保存按页拼接的文本，不保存文本块坐标、表格单元格和阅读顺序证据。这会削弱定位、表格语义和跨条款比对。
3. **主要漏检原因是审查架构覆盖不足。** 当前确定性规则只支持关键词、单一比例、文本位置顺序和必需词存在性；当前默认配置没有可执行的分析模型。即使启用模型，模型也只收到全文和有限依据，输出契约只有一个泛化的 `risks` 数组，没有事实抽取、金额计算、时间关系、主体角色、缺失项清单和覆盖率门禁。

因此，推荐的方向是：

```text
版面保真解析
  -> 条款/表格/实体事实抽取
  -> 金额、时间、主体、义务关系图
  -> 确定性校验引擎
  -> 语义模型候选发现与解释
  -> 引用、定位、证据和覆盖率 Validator
  -> 风险清单与人工复核
```

语义模型应当是分层链路中的一部分，而不是唯一的风险发现器。

### 2.3 当前链路复现

用实际 DOCX 解析结果、默认选中的 `procurement-rules@2.1` 和 `contract-common@1.0` 复现，派生出的可执行规则只有：

```text
procurement-rules@2.1:prepayment-ratio
  type=amount_ratio, threshold=0.30

contract-common@1.0:signature
  type=required_clause, keyword=授权代表签字
```

实际合同使用“合同总价款的 50%/40%/15%”，没有“预付款”或“付款比例”这一触发短语；签署页写的是“法定代表人／委托代理人（签字）”，也不包含“授权代表签字”。因此当前引擎产生的是两个泛化的待核验/候选项，且定位回退到第 1 页开头，任务仍可能被标记为 `completed`。

当前默认样例状态中的 `capabilityData.models` 为空，进一步说明在未手工配置并启用 `analysis` 模型时，`runReview()` 不会进入模型调用分支。

项目现有自动化测试共 54 项，当前均通过；但测试覆盖的是解析器边界、规则示例和流水线契约，没有用这份 26 项 ground truth 合同做端到端召回率验收。因此“测试通过”不能推出“合同风险覆盖达标”。

## 3. 26 项风险与能力缺口映射

`风险清单.md` 标记了 26 个真实缺陷，严重度为致命 8、重要 14、轻微 4。它们并非同一种“语义风险”，需要不同的检查器。

| 风险编号 | 真实问题 | 现有缺口 | 应由谁负责 |
|---|---|---|---|
| 1-4 | 大小写金额、明细合计、分期比例和分期金额互相冲突 | 没有中文大写金额归一化、表格行列结构、金额求和和跨条款三角核对 | 金额事实抽取 + 算术引擎 |
| 5-9 | 违约金叠加、无限上限、过高日费率、双方不对称、无累计上限 | 没有处罚条款模式、年化计算、累计上限和同一违约行为识别 | 责任/违约规则引擎 + 语义候选 |
| 10-12 | 付款主体倒置、交付义务主体倒置、错别字 | 没有甲乙方角色图、主谓宾/义务结构和文本质量检查 | 主体义务抽取 + 文本质量引擎 |
| 13-15 | 验收期限冲突、15 日小于 30 日、工作日/自然日混用 | 没有时间单位归一化、事件顺序图和矛盾检测 | 时间事实抽取 + 时序引擎 |
| 16 | 争议管辖落在乙方所在地 | 没有主体地址、所在地和管辖偏好之间的关系 | 主体/地域关系引擎 + 企业规则 |
| 17-18 | 环境准备和复检费用责任单方转嫁 | 没有“义务-条件-责任方-费用方”矩阵 | 义务分配引擎 |
| 19-23 | 单方解除、终止后数据处置、知识产权侵权兜底、保密责任、持续合规保证缺失 | 没有合同类型的必备条款矩阵和“缺失项”结果类型 | 完整性检查引擎 + 语义模型 |
| 24-25 | 验收标准主观化、“重大故障”未定义 | 没有验收指标词典、阈值和定义引用检查 | 验收质量引擎 |
| 26 | 许可永久与合同有效期三年冲突 | 没有期限对象、许可期限与合同期限的关系约束 | 时序/期限关系引擎 |
| A1-A5 | 生效日不确定、罚则量纲不可比、数据恢复期限缺失、暂缓付款无期限、附件位阶表述不统一 | 没有附加观察和非阻断质量检查的独立类别 | 语义模型 + 质量检查引擎 |

核心判断是：这 26 项中只有少部分可以由关键词命中；大多数需要先把合同转换成事实、关系和约束，再做校验。

## 4. 目标架构

### 4.1 解析层：从纯文本升级为证据块

保留现有 `document.text` 作为兼容字段，同时增加结构化 `blocks`：

```json
{
  "block_id": "block_2_17",
  "file_version_id": "contract_v1",
  "source_type": "docx|pdf|ocr",
  "page": 2,
  "logical_page": 2,
  "block_type": "paragraph|heading|table|table_cell|header|footer",
  "clause_no": "2.2",
  "text": "合计 1,286,000",
  "bbox": [88, 620, 510, 648],
  "table_ref": {"table_id": "table_2", "row": 5, "column": 5},
  "char_range": [1840, 1853],
  "text_hash": "sha256:..."
}
```

DOCX 解析要求：

- 直接读取 OOXML 段落、标题、表格、行、列、合并单元格和分页信息；
- 记录 `table_id/row/column`，不能只把表格拼为连续字符串；
- 保留原始顺序和规范化文本的映射；
- 物理页码不能凭文本长度伪造。若需要显示页码，应通过确定版本的 DOCX 渲染器生成 PDF 后建立页映射；否则标记为 `logical_page` 或 `page_unresolved`；
- 保留解析警告，并把 `w:tblPrEx` 等非核心 OOXML 忽略项写入 `parse_warnings`。

PDF 解析要求：

- 保存文本 item 的 bbox、字体和阅读顺序；
- 基于坐标重建行、段落和表格候选；
- 识别页眉、页脚和页码，避免把页脚数字误当金额；
- 纯扫描页必须进入 OCR 分支，低置信度区域不得作为 `verified` 证据。

### 4.2 事实层：建立可计算的合同事实

建议引入以下事实对象，所有事实都必须带证据锚点和置信度：

| 事实 | 最小字段 | 本合同示例 |
|---|---|---|
| `PartyFact` | `party_id`、别名、全称、地址、所在地、角色 | 甲方长沙，乙方武汉 |
| `MoneyFact` | 原文、数值、币种、税含、条款、表格位置 | `壹佰贰拾捌万陆仟` 与 `1,268,000` |
| `RatioFact` | 数值、分母、付款阶段、金额 | `50%/40%/15%` |
| `DateFact` | 日期/期限、起算事件、单位、工作日类型 | 10 工作日、15 自然日、30 自然日 |
| `ObligationFact` | 义务方、相对方、动作、标的、条件、责任后果 | “甲方应向甲方提供” |
| `PenaltyFact` | 触发行为、计算基数、费率、固定额、是否叠加、上限 | 8.1、8.3、8.4、8.5 |
| `AcceptanceFact` | 初验/终验、触发事件、标准、指标、视为通过 | “满足甲方使用需求” |
| `ClausePresenceFact` | 检查项、是否存在、是否完整、关联条款 | 单方解除权、数据处置 |

金额和比例必须使用定点 decimal 或字符串持久化，禁止使用二进制浮点直接作为合同金额。

### 4.3 关系层：把条款变成图

至少建立四类关系：

- **引用关系**：8.3 引用 8.1，4.2/4.3 与 11.4 都描述验收；
- **数值约束关系**：2.1 总价、2.2 明细、2.3 分期、附件一合计；
- **时序关系**：交付、初验、试运行、终验、付款和合同期满；
- **主体义务关系**：甲方/乙方、付款方/收款方、义务方/责任方。

风险不是孤立的字符串命中，而是对关系图执行约束后得到的 `conflict`、`missing` 或 `unverifiable`。

## 5. 检查引擎设计

### 5.1 金额与比例引擎

检查项至少包括：

1. 中文大写金额与阿拉伯数字相互转换并比较；
2. 价格表按行计算 `数量 x 单价`，再与小计、合计比较；
3. 分期比例求和必须等于 100%；
4. 分期金额与确认后的总价、比例同时校验；
5. 正文、附件、报价单等多个来源形成金额三角核对；
6. 记录每个计算式、输入事实、舍入规则和证据引用。

本合同应至少生成以下可解释结果：

```text
2.1 大写金额 = 1,286,000；小写金额 = 1,268,000；差额 = 18,000
2.2 明细合计 = 1,286,000；与 2.1 小写金额冲突
2.3 比例合计 = 50% + 40% + 15% = 105%
2.3 分期金额按 1,268,000 计算；与 2.2 合计 1,286,000 不一致
附件一合计 = 960,000；与 2.2 的软件许可行一致，但不能代表合同总价
```

### 5.2 时间与期限引擎

统一表示：`event`、`duration`、`calendar_type`、`start_condition`、`end_condition`。检查：

- 同一事件的多个期限是否冲突；
- 15 日是否早于必须先完成的 30 日试运行；
- 工作日和自然日是否混用且没有定义；
- 永久许可与三年合同期的存续关系是否明确；
- 签订、生效、交付、初验、终验、付款、终止的事件图是否可执行。

### 5.3 主体与义务引擎

对“谁应当向谁做什么、未完成会承担什么”进行结构化抽取，并检查：

- 义务方与受益方是否为同一主体；
- 付款方和收款方是否倒置；
- 乙方实施所需环境是否被全部转嫁给甲方；
- 质量问题导致的复检费用是否仍由甲方承担；
- 责任后果是否与触发方一致。

### 5.4 违约责任与责任边界引擎

至少识别：

- 同一违约行为的多条罚则是否叠加；
- 日费率年化后的数量级；
- 双方违约金基数和费率是否明显不对称；
- 是否有累计上限、总责任上限和例外；
- 直接损失、间接损失、可得利益、第三方索赔是否被无上限纳入；
- 固定违约金与数据恢复义务是否具有期限和不可恢复处理。

### 5.5 完整性和缺失项引擎

“未发现关键词”不能直接等同于“条款缺失”。应为每种合同类型维护版本化检查清单，例如采购/软件实施合同至少检查：

- 甲方单方解除权及触发情形；
- 合同终止后的软件停用、账号注销、数据导出、返还和删除确认；
- 第三方知识产权侵权的通知、抗辩、替换和费用承担；
- 保密义务的违约责任；
- 供应商资质和产品持续合规保证；
- 可量化验收指标和“重大故障”定义。

每个检查项都要产生执行状态：`pass`、`conflict`、`missing`、`unverifiable`、`not_applicable`，即使没有形成风险，也要记录已检查。

## 6. 语义模型的正确职责

模型应从“自由审查全文”改为“围绕事实和检查计划的受约束推理”：

1. `extraction` 模型负责从解析块中抽取事实，不负责直接确认风险；
2. 确定性引擎先做金额、比例、时间、主体和规则计算；
3. `analysis` 模型负责解释冲突、发现语义变体、提出缺失项候选和补充检查；
4. 模型输出必须逐个绑定 `check_id`、事实 ID、原文 block ID 和关联条款；
5. 没有可回溯原文时只能返回 `unverifiable`，不能生成带伪页码的风险；
6. 模型声称 `confirmed` 也不能绕过人工复核和 Validator。

建议输出契约如下：

```json
{
  "schema_version": "risk-review-v2",
  "coverage": [
    {"check_id": "amount.total_vs_uppercase", "status": "conflict", "fact_refs": ["money_1", "money_2"]},
    {"check_id": "termination.data_disposition", "status": "missing", "fact_refs": []}
  ],
  "risk_candidates": [
    {
      "risk_topic": "amount_consistency",
      "risk_level": "critical",
      "conclusion_status": "candidate",
      "evidence_status": "verified",
      "related_checks": ["amount.total_vs_uppercase", "amount.schedule_sum"],
      "contract_location": {
        "block_ids": ["block_2_11", "block_3_03"],
        "page": 2,
        "clause_no": "2.1",
        "quote": "人民币壹佰贰拾捌万陆仟元整（小写：¥1,268,000 元）"
      }
    }
  ]
}
```

模型上下文应按条款和关系分块，而不是仅用全文前后截断。上下文快照要记录保留的条款、被省略的条款、模型配置版本和检查覆盖范围。

## 7. 证据与 Validator 改造

### 7.1 定位规则

- `quote` 必须能在对应 block 的规范化文本中精确匹配；
- 保留原文片段、规范化片段、`text_hash`、`char_range` 或 `bbox`；
- 匹配失败时使用 `location_status=unresolved`，不能回退到第 1 页第一段；
- DOCX 没有可靠物理页码时显示“逻辑页/段落/表格单元格”，不能伪造页码；
- 多条款风险要同时保存多个 location，而不是强行归入一个条款。

### 7.2 任务完成条件

任务 `completed` 必须同时满足：

- 解析状态可用，且解析警告已处理或明确降级；
- 合同类型对应的检查清单已执行并记录覆盖率；
- 每个高风险结果有原文和证据状态；
- 关键算术和时序检查没有被跳过；
- 模型失败时任务为 `partial` 或 `input_required`，不能静默以 0 条风险完成。

### 7.3 结果展示

风险清单之外，审查工作区应显示：

- 本次执行了多少检查项、通过/冲突/缺失/无法判断各多少；
- 风险来源是确定性规则、事实校验、语义模型还是人工新增；
- 解析质量警告、模型是否实际调用、被截断的上下文范围；
- “0 条风险”是“已完成检查且无候选”，还是“没有模型/规则未覆盖”。

## 8. 实施优先级

### 阶段一：解析保真与可观测性

- 增加 `blocks`、表格单元格、文本哈希、坐标/逻辑页和解析警告；
- 修复无引用时回退第 1 页的问题；
- 保存实际执行的规则、检查项、模型和上下文快照；
- 将当前合同加入回归夹具，但暂不改变风险定级策略。

### 阶段二：确定性事实与高价值校验

- 中文大写金额、阿拉伯金额、比例、数量、日期和工作日/自然日规范化；
- 实现金额三角核对、比例求和、分期金额重算；
- 实现主体义务倒置、时间顺序、违约金叠加/封顶和赔偿范围检查；
- 对每个检查项输出结构化 `check_result`。

### 阶段三：语义覆盖和缺失项

- 建立采购/软件实施合同必备条款矩阵；
- 引入 extraction 与 analysis 两个模型角色；
- 模型围绕检查项输出事实引用和缺失候选；
- 加入“未执行检查项不得标记 completed”的门禁。

### 阶段四：跨文件、OCR 与检索增强

- 支持合同、报价单、订单、技术需求书和附件的统一事实图；
- 接入 OCR 和低置信度区域处理；
- 在关键词检索之外增加向量、实体和条款关系召回，并保存检索证据；
- 将跨文件金额/日期冲突纳入同一套 Validator。

## 9. 回归评测与验收标准

### 9.1 必测指标

使用 `风险清单.md` 作为 ground truth，至少计算：

| 指标 | 目标 |
|---|---:|
| 致命项召回率（1、2、3、5、6、10、11 等致命项） | 100% |
| 26 项总体召回率 | 不低于 80% |
| 误报数量 | 不超过 3 项 |
| 严重度定级准确率 | 单独统计并持续提升 |
| 跨条款关联 | 2.1/2.2/2.3 和 4.2/4.3/11.4 两组关系必须被指出 |
| 缺失项识别 | 19-23 至少全部进入 `missing` 或 `unverifiable` |
| 定位有效率 | 每条已验证风险的 quote 必须能回溯到 block |

### 9.2 自动化测试分层

1. **解析测试**：DOCX 表格、段落和 PDF 坐标能转换为统一 block；DOCX/PDF 的关键事实集合一致。
2. **事实测试**：金额、百分比、日期单位、主体和罚则事实抽取可重复。
3. **引擎测试**：每个风险组至少一个正例、一个反例、一个无法判断例。
4. **端到端测试**：实际合同运行后检查 26 项召回、严重度、证据、定位和覆盖率。
5. **降级测试**：模型未配置、模型超时、OCR 不可用、引用失配时，任务必须明确为部分完成或待输入。
6. **回归测试**：同一合同重复审查不得因风险去重或模型重试丢失不同条款的风险。

### 9.3 本合同的验收样例

最小通过结果应至少包含：

- 金额组 1-4 的计算式和三处原文锚点；
- 违约责任组 5-9 的叠加、费率、对称性和上限分析；
- 主体倒置 10-12 的主语/宾语结构；
- 期限组 13-15、26 的事件图；
- 争议管辖 16 的主体所在地证据；
- 义务转嫁 17-18 的责任/费用分配；
- 缺失条款 19-23、验收标准 24-25 的 `missing` 检查结果；
- A1-A5 作为非阻断附加观察单独展示，不与致命风险混为一谈。

## 10. 不建议的做法

- 只把当前模型提示词改长，不补事实 schema 和确定性计算；
- 只增加更多关键词规则，把“存在关键词”当成“条款完整有效”；
- 继续将 DOCX 整体视为一页，再用字符位置推导页码；
- 在 quote 匹配失败时回退到第 1 页第一段；
- 用模型自由生成的法律结论覆盖未验证证据；
- 只看风险数量，不看检查覆盖率和未执行项；
- 以现有 54 个单元测试全部通过为理由，跳过真实合同回归评测。

## 11. 最终判断

对“是原始合同解析有问题，还是单靠语义解析不够完整”的回答是：

> **原始解析存在结构保真不足，但没有丢掉本合同大多数关键文字事实；主要问题是当前审查链路没有把事实转成可计算、可关联、可验证的检查结果，且语义模型并非默认必经步骤。单靠语义解析不能稳定覆盖这 26 项风险。**

本合同最适合用作第一份端到端能力夹具：它同时覆盖金额计算、条款关系、主体倒置、时序冲突、责任边界、缺失条款和验收质量。完成阶段一至阶段三后，再用本清单验收，才能判断系统是否真的具备“合同风险审查能力”，而不是只具备“从合同中生成一些风险文本”的能力。

## 12. 本轮改造落地状态

### 12.1 已实现

- `electron/parser.cjs` 已输出统一 `document.blocks[]`：DOCX 段落、标题和表格单元格保留 `table_ref`、逻辑页、字符范围和 SHA-256 文本哈希；PDF 保留页级证据块、页码、整页边界和哈希。DOCX 的字符范围映射回原始 `document.text`，可区分重复段落，不再使用压缩空白后的偏移。没有可靠物理分页时明确标记 `page_status=unresolved`，不伪造页码。
- 新增 `electron/contract-facts.cjs`：可抽取中文大写/阿拉伯金额、比例、工作日/自然日期限、主体地址、义务关系和违约金事实；事实均带 `source_refs`、原文和置信度。
- 新增 `electron/contract-checks.cjs`：已落地金额勾稽、分期比例、分期金额锚点、验收时序、主体倒置、违约金叠加/封顶、赔偿范围、争议管辖、保护性条款缺失、验收标准和许可期限等检查；已补充双方违约费率不对称、时间单位混用、环境义务转嫁和验收费用分配检查。
- `runReview()` 已在旧规则和可选模型之前执行事实抽取与确定性检查，并持久化 `review.contract_facts`、`review.check_results`、`review.coverage`、`review.fact_warnings`；原有 `document.text`、`document.pages` 和 `review.risks` 保持兼容。
- 覆盖率字段固定为 `total/executed/passed/conflict/missing/unverifiable/not_applicable/skipped`。`executed` 仅统计 `pass/conflict/missing`，不适用、不可验证和跳过项分别计数；生成器与 Validator 使用相同口径。结构化文档的关键检查无法执行时任务降级为 `partial` 并返回 `CRITICAL_CHECKS_INCOMPLETE`。
- 新增 `general-checklist-catalog.json` 和 `general-checklist.cjs`，按 `GC-1.0-2026-09-16` 保存 95 项通用判据、适用条件、证据要求和检查状态，持久化为 `checklist_version/checklist_results/checklist_coverage`。专项检查映射、文本筛查、语义复核和外部材料核验分别记录实际方法；模型收到 `check_plan`，空风险结果不会把未核验项改成通过。高风险通用项仍不可验证时，结构化文档任务返回 `CHECKLIST_REVIEW_REQUIRED` 并保持 `partial`。
- 模型引用匹配失败不再回退到第一页文本，而是返回 `location_status=unresolved`、空 quote、空页码和零定位置信度；`confirmed` 仍不能绕过人工复核。
- Validator 已校验覆盖率一致性、关键检查跳过、高/严重风险未解析定位，并分别返回 `COVERAGE_INVALID`、`CRITICAL_CHECK_SKIPPED`、`HIGH_RISK_LOCATION_UNRESOLVED`。
- 已加入双格式 Golden Set 回归：两份真实合同均执行 24 项确定性检查，覆盖金额、时序、主体、违约、缺失条款和验收质量；同时逐项比对 95 项通用清单状态、检查覆盖率、关键风险证据和任务状态。PDF 违约事实的条款号按费率、金额或责任关键词所在位置确定，避免前导空白及相邻标题造成条款归属错位。

### 12.2 当前回归结果与边界

在无分析模型、无外部知识材料的回归配置下，两种格式的检查状态一致：

| 检查集合 | 总数 | 已执行 | 通过 | 冲突 | 缺失 | 不可验证 | 不适用 | 跳过 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 确定性检查 | 24 | 24 | 0 | 19 | 5 | 0 | 0 | 0 |
| 通用清单 | 95 | 30 | 1 | 11 | 18 | 53 | 12 | 0 |

专项检查与通用清单存在映射关系，上述数量不能相加作为独立风险数；合并后均为 42 条候选风险。通用清单的 53 项不可验证结果中有 31 项高风险，因此两种格式的任务均为 `partial`，错误码为 `CHECKLIST_REVIEW_REQUIRED`。确定性检查的 100% 执行率不代表通用清单已经全部核验，也不代表对 26 项真实缺陷的召回率。

DOCX 提取 157 个证据块，其中 84 个单元格属于 6 张表；PDF 提取 7 个整页证据块。回归校验了所有块的字符范围与正文匹配，以及关键风险引文确实位于其引用块内。DOCX 的物理页码仍未实现，只能提供逻辑块/表格单元格定位；Validator 可验证块 ID、文本哈希和块内字符范围，不再要求伪造物理页码。风险证据及人工确认门禁仍独立保留。

事实记录仍存在格式粒度差异：DOCX 有 54 条、PDF 有 52 条；PDF 将相邻地址与联系方式合并成一个候选，DOCX 另有一条仅命中违约责任标题的记录。对跨字段地址已输出 `PARTY_ADDRESS_SEGMENTATION_UNCERTAIN`，绑定事实与原文引用，并将置信度降至 0.4，后续需依据表格或版面核验，不能据此声称两种格式的完整事实集一致。缺失条款结果表达“未在当前合同文本中发现完整条款”，不等同于法律意见或自动确认结论。
